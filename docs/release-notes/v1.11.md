# Domain AI v1.11

**Local-first AI chat for Android. Your words stay on your device.**

Domain AI answers every message on-device by default, with zero network access. The
cloud is strictly opt-in — gated by a network kill switch and a redactor that strips
sensitive information from your prompt before it's sent to a cloud model.

## Faster on-device replies

The native engine was being built for a baseline ARM target, which quietly left
ggml's accelerated integer kernels out of the binary — they compile only when the
build asks for dot-product or i8mm support, and it never did. Those kernels do
the quantized matrix multiplication that is most of the work in both reading your
prompt and generating each token.

Rather than pick one CPU generation and abandon everything older, the engine now
ships its compute kernels once per ARM feature tier — baseline ARMv8.0 up through
ARMv9.2 with SME — and picks the fastest set your phone actually supports when it
starts. Recent silicon gets dot-product, i8mm, SVE2 or SME kernels; older arm64
devices keep working exactly as before. The llamafile/tinyBLAS kernels are
enabled alongside them and gate on the same features, so the two compound.

Two further changes cut memory pressure, which is usually what limits a phone
before arithmetic does:

- **The key/value cache is now quantized** (q8_0), roughly halving the memory
  traffic that dominates long-context decoding and freeing RAM for a bigger
  context. A model that can't support it falls back to full precision on its own.
- **The prompt compute buffer is right-sized.** It had been scaling with the
  device-adaptive batch size, so a high-RAM phone reserved a buffer sized for
  4096 tokens to chase prefill gains that had already flattened out.

The trade-off is a larger download, since the APK now carries a set of CPU kernel
modules rather than a single one. Next to the 0.7–1.6 GB model files it runs, the
difference is small.

## What's new since 1.08

- **Regenerate a reply.** Every finished reply now carries a regenerate control: the
  answer is thrown away and the same question is asked again. Routing is decided
  afresh, so regenerating right after switching profile, model, context length or
  thread count uses the new settings — which is exactly when you want it, because an
  on-device answer that came out truncated, repetitive or plain wrong no longer leaves
  you retyping the prompt into a new turn.
- **Edit and resend a question.** Any message of yours can be reworded and asked
  again. The conversation continues from that turn, so the answers that followed are
  replaced — and the dialog tells you how many messages that is before you confirm,
  rather than dropping them silently. Reword the opening question and the chat's title
  follows the new wording.
- **Copy your own messages.** Your messages now carry a copy control alongside edit,
  so a long prompt is easy to reuse.

Only the newest reply offers regenerate — regenerating an older one would quietly
discard everything said after it — and both controls are hidden while a reply is still
streaming.

## Under the hood

Both actions are the same move: rewind the conversation to just before a question, then
send it back through the ordinary send path. There is no second generation path, so a
redone turn is routed, redacted, history-budgeted and stored encrypted exactly like a
fresh message. The rewind rules are pure functions on the conversation model and are
covered by JVM unit tests — including the awkward cases: the rolling summary can never
claim messages that no longer exist, the summary is dropped when a chat is emptied, and
an emptied chat releases its title so a reworded question can rename it.

## Requirements

- Android 8.0+ (API 26), arm64-v8a devices only. No particular CPU generation is
  required — the engine selects kernels to match, as described above.
- A GGUF model (download in-app or import your own) for on-device replies.
